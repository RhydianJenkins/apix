# AGENTS.md

Guidance for AI coding agents (and humans) working in this repository. `apix`
is a CLI HTTP and gRPC client that manages requests across multiple named API
domains, with discoverability via OpenAPI, GraphQL introspection, or gRPC
server reflection. For feature background and end-user FAQ, read
[`README.md`](./README.md) first - this file focuses on *working on apix
itself*.

## Project layout

- `cmd/apix/` - the cobra command tree (`main.go` + one file per
  command family: `http.go`, `grpc.go`, `auth.go`, `header.go`, `show.go`).
  Commands here only parse flags/args and call into `internal/handlers`; keep
  them thin.
- `internal/handlers/` - the actual command implementations (`NewHandler`,
  `StatusHandler`, `GraphQLShowHandler`, etc).
- `internal/config/` - the YAML config model (`Domain`, `CfgPaths`) and
  read/write logic, built on `viper`.
- `internal/httpclient/`, `internal/grpcclient/`, `internal/graphqlclient/`,
  `internal/oas/` - protocol-specific clients and discovery (OAS parsing,
  GraphQL introspection, gRPC reflection).
- `internal/grpctest/` - a reusable in-process gRPC+reflection test server,
  used by `grpcclient`/`handlers` tests instead of mocking.
- `examples/*.yaml` - runnable example configs referenced from the README
  (`apix -c ./examples/pokeapi.yaml get ...`); keep these working.

When adding a command: add the thin `cobra.Command` wiring in `cmd/apix`,
put the logic in a new `internal/handlers` file, and add table-driven tests
next to both, following the existing `*_test.go` files as the template.

## Setup & running apix locally

This project is developed with Nix (`flake.nix`); `.envrc` runs `use flake`
if you have direnv.

```sh
nix develop            # dev shell with go, gopls, semgrep
nix run .#build        # builds ./apix with the version ldflag set correctly
./apix -c ./examples/pokeapi.yaml get /api/v2/pokemon/ditto
```

Without Nix, a plain `go build -o apix ./cmd/apix` also works for local
iteration (you just won't get an embedded version string).

## Validating changes

Always run before considering a change done:

```sh
go vet ./...
gofmt -l .              # should print nothing
go test ./...
```

`nix flake check` runs the equivalent (`go vet` + `go test -v`) plus a build,
and is exactly what CI (`.github/workflows/ci.yaml`) runs on every PR, along
with a `./result/bin/apix --help` smoke test. Prefer running `nix flake
check` when Nix is available since it's the closest thing to CI locally.

Tests follow the existing table-driven style with `t.TempDir()` for scratch
config files, `t.Cleanup(func() { viper.Reset() })` whenever a test mutates
`config.CfgPaths` or domain state, and `internal/grpctest` for anything that
needs a real gRPC server. Match that style rather than introducing mocks.

## Commit conventions & releases

Commits **must** follow [Conventional Commits](https://www.conventionalcommits.org/)
(`feat:`, `fix:`, `docs:`, `test:`, `chore:`, `refactor:`, ...) - this repo is
versioned by [Release Please](https://github.com/googleapis/release-please)
(`release-please-config.json`), which parses commit history to bump the
version and regenerate `CHANGELOG.md`. In practice:

- `feat:` -> minor bump, appears in the changelog's "Features" section.
- `fix:` -> patch bump, appears under "Bug Fixes".
- `docs:`, `chore:`, `test:`, `ci:`, `refactor:`, `style:`, `build:` -> no
  version bump, hidden from the changelog (see `changelog-sections` in
  `release-please-config.json`).
- A `!` after the type, or a `BREAKING CHANGE:` footer, triggers a major bump.

Never hand-edit `CHANGELOG.md` or `.release-please-manifest.json` - they're
generated by the Release Please bot via its own PRs.

## Conventions worth knowing

- Module path is `github.com/rhydianjenkins/apix/v3` - a major version bump
  means updating this import path everywhere (see `go.mod`).
- `internal/config.CfgPaths` defaults to the real, expanded `$HOME` at
  process start, not a literal `"~"`. If you generate or compare CLI output
  that includes the `--config` flag's default, pin `CfgPaths` to a
  placeholder first so output stays stable across machines/CI (see how
  `cmd/apix` tests reset `config.CfgPaths` and `viper.Reset()`).
- `cmd/apix` file names are mixed-case where they mirror an exported type
  (e.g. `internal/handlers/HTTPHandler.go`, `GRPCHandler.go`) alongside
  lowercase files elsewhere - match the existing file's casing in the
  package you're editing rather than renaming for consistency.

Commands and version strings in this file and in `README.md` were checked
against this repository as of this writing; re-verify them with the commands
above if `flake.nix` or `cmd/apix` changes.
